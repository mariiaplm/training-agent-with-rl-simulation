# Elevator Agent — Reinforcement Learning Simulation

A Q-learning agent that learns to operate a 5-floor elevator. Nobody tells it the rules of
good elevator behavior, no "go to the nearest call," no "finish the trip before picking up
someone new." It only ever receives a number saying how well the last moment went, and it
works the rest out itself over thousands of simulated runs.

The result is watchable in the browser: a live replay of the trained agent running the
building, with the reward and delivery count updating as it goes.

## What it actually does

Every timestep, the agent:

1. observes the state of the building,
2. picks one of three actions — **up**, **down**, or **open doors**,
3. receives a reward, and
4. observes the new state.

That loop runs about four million times during training. Each pass nudges a table of value
estimates, and good behavior gradually falls out of the numbers.

**It is not a neural network.** It's tabular Q-learning: a dictionary mapping every state the
agent has encountered to three numbers, one per action, each estimating "how much total future
reward can I expect if I do this here." Picking the best action is just taking the largest of
the three.


## How it's implemented

### State

The agent sees a tuple of three things:

```python
(current_floor, calls, destinations)
```

- `current_floor` — an integer, 0 to 4
- `calls` — five booleans: is someone waiting on this floor?
- `destinations` — five booleans: does a rider onboard want this floor?

That's 5 × 2⁵ × 2⁵ = **5,120 possible states**, small enough for a table to cover thoroughly.
The tuple has to be immutable because it's used directly as a dictionary key.

### Actions

| value | meaning |
|---|---|
| `0` | move up one floor |
| `1` | move down one floor |
| `2` | stay put and open the doors |

Doors only operate on action `2`. That's intentional. It forces the agent to decide *when*
stopping is worth it, rather than getting boarding for free.

### Rewards

This is where all the behavior comes from. The agent is never told what to do, only what things
cost:

| event | reward |
|---|---|
| passenger delivered | **+10.0** |
| passenger boarded | **+1.0** |
| each move | **−0.1** |
| per waiting passenger, per timestep | **−1.0** |
| per onboard passenger, per timestep | **−0.5** |

The ratios matter more than the absolute numbers. Waiting has to hurt enough that moving is
clearly worth it, and delivery has to pay enough to justify several timesteps of travel.
"Serve the nearest call first" is not written anywhere. It's what these five numbers add up to.

### Learning rule

Standard Q-learning update:

```
Q[s][a] += ALPHA * (reward + GAMMA * max(Q[s']) - Q[s][a])
```

The `max(Q[s'])` term is what lets value propagate backwards: moving toward a waiting passenger
becomes valuable *because* it leads to a state where opening the doors is valuable, which leads
to a delivery.

### Hyperparameters

| name | value | what it controls |
|---|---|---|
| `ALPHA` | 0.1 | learning rate — how far each experience shifts an estimate |
| `GAMMA` | 0.95 | discount — how much future reward counts vs. immediate |
| `EPSILON_START` | 1.0 | starts fully random |
| `EPSILON_MIN` | 0.05 | never stops exploring entirely |
| `EPSILON_DECAY` | 0.9995 | per-episode decay |
| `EPISODES` | 20,000 | training runs |
| `MAX_STEPS` | 200 | timesteps per episode |
| `ARRIVAL_RATE` | 0.05 | chance per floor per timestep of a new passenger |


## Files

| file | role |
|---|---|
| `elevator_env.py` | The world: state, rules, rewards. Makes no decisions. |
| `train.py` | Q-learning: the table, action selection, the update rule, the training loop. |
| `main.py` | Watch the trained agent run in the terminal. |
| `export_run.py` | Record one trained run and write it out as `run.js`. |
| `index.html` / `index.css` | Browser visualization that replays `run.js`. |
| `q_table.pkl` | The trained agent — generated by `train.py`. |
| `run.js` | One recorded run — generated by `export_run.py`. |

The split between `elevator_env.py` and `train.py` is the important one. The environment knows
physics and consequences; the agent knows strategy. Neither knows anything about the other's
job.


## Running it

No dependencies beyond the Python standard library. Python 3.9+.

```bash
git clone <your-repo-url>
cd <repo>
```

**1. Train the agent** (a few minutes — 20,000 episodes × 200 timesteps):

```bash
python train.py
```

Prints progress every 500 episodes and writes `q_table.pkl` when finished.

**2. Watch it in the terminal:**

```bash
python main.py
```

**3. Record a run for the browser:**

```bash
python export_run.py
```

Writes `run.js`.

**4. Open the visualization:**

Open `index.html` in any browser. No server needed.


## Results

| policy | average reward per episode |
|---|---|
| random actions | **−557** |
| trained agent | **+100 to +150** |

Training crosses zero around episode 3,000 and plateaus by roughly episode 8,000. The remaining
variance between episodes is the environment's own randomness — passengers spawn by dice roll,
so some runs are simply busier than others — plus the 5% of actions still taken at random.


## Known issues and limitations

**Passengers are booleans, not objects.** Each floor tracks only *whether* someone is waiting,
not how many. A second person arriving on a floor that already has a call is invisible. This
keeps the state space small enough for a table, at the cost of realism.

**Destinations are assigned at boarding, at random.** When someone gets in, the environment
picks a random other floor for them. Individual passengers aren't tracked, so two riders wanting
the same floor collapse into one flag.

**Calls have no direction.** A real elevator distinguishes "I want to go up" from "I want to go
down" on the same floor. This one doesn't, which removes a chunk of real scheduling difficulty.

**No capacity limit.** The car will hold any number of riders.

**`q_table.pkl` goes stale if you change the rewards.** The saved table reflects the reward
function it was trained under. Change any of those numbers and you have to retrain, or the agent
will be optimizing for a world that no longer exists.

**Pickle files execute code when loaded.** Don't load a `.pkl` from a source you don't trust.
Your own training output is fine.
